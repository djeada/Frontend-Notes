# UI components: behavior, labels, and accessibility

[Original UI chapter](../07_ui.md) · [All chapter updates](README.md)

An interface is successful when people can understand the available actions and operate them through different input methods. Color, spacing, and typography help communicate hierarchy, but semantic HTML, keyboard interaction, focus, and error messages are part of component design too.

## Corrections to component descriptions

- A native `<select>` is a **select/listbox control**, not automatically an ARIA *combobox*. A true combobox has distinct value and popup behavior, often with text input and autocomplete. Prefer native controls unless the extra complexity is justified.
- Placeholders are examples or hints, **not replacements for persistent visible `<label>` elements**. They disappear as people type and do not always communicate required format or errors.
- A menu is not interchangeable with a site navigation list. Use `<nav>` with normal links for navigation; menu roles imply an application-style keyboard interaction model.
- A radio group allows **at most one** choice, but may initially have zero choices unless one is required or preselected. Saying it always selects “exactly one” is too absolute.
- Avoid vague buttons such as “Submit” when a specific action like “Create account” better describes the result. Do not depend on color alone to distinguish primary actions or errors.

## Accessible native form pattern

```html
<form action="/subscribe" method="post">
  <fieldset>
    <legend>Newsletter frequency</legend>
    <label><input type="radio" name="frequency" value="weekly" required> Weekly</label>
    <label><input type="radio" name="frequency" value="monthly"> Monthly</label>
  </fieldset>
  <label for="contact">Email address</label>
  <p id="contact-help">We use this only to send the newsletter.</p>
  <input id="contact" name="email" type="email" autocomplete="email"
         aria-describedby="contact-help" required>
  <button type="submit">Subscribe</button>
</form>
```

`fieldset` and `legend` convey the group question. A shared `name` makes the radio choices mutually exclusive. Associated helper text supplements, rather than replaces, the label. Validate the email again on the server and present server errors in text near the relevant control.

## Practical acceptance criteria

Check the page at 200% zoom and on narrow screens; ensure no essential content is clipped. Make keyboard focus visible and preserve a logical focus order. Verify text contrast against the actual background (WCAG AA generally requires 4.5:1 for normal text and 3:1 for qualifying large text). For required non-text UI boundaries and states, evaluate the relevant 3:1 criterion. Confirm icon-only controls have accessible names and that errors are not communicated by a red border alone.

## Practice

Build the same preference form using native elements before trying a custom component. Tab through it, select each radio option using the keyboard, trigger a validation error, and check the accessible names in browser developer tools.
